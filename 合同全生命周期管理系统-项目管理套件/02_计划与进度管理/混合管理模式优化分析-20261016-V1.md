# 混合项目管理下总控计划与周迭代计划的优化分析

**项目**：能源行业合同全生命周期管理系统
**版本日期**：2026-10-16
**性质**：分析与优化建议（只读诊断，未改动任何工作簿）；涉及基线与结构变化的建议须走评审/变更流程后方可实施

---

## 一、现状诊断

### 1.1 两簿当前形态

| 维度 | 项目总控台账 | 周迭代计划 |
| --- | --- | --- |
| 定位 | 全量 WBS：135 个任务（T001-T095 实施任务 + T096-T135 系统工作包），四级功能层级，挂批次（MS001-MS0xx） | 周承诺制迭代：按"迭代周"列归桶任务，明细 INDEX/MATCH 联动总控，汇总自动统计完成率/延期/暂停 |
| 状态驱动 | **人工维护四专业执行明细**（业务/后端/前端/测试 各 4 列共 16 列：负责人/状态/开始/结束），再由公式推导计划开始/完成（MIN/MAX）、综合进度（加权）、延期状态 | 明细状态引用总控；汇总公式统计；周目标/复盘/专业阶段为人工列 |
| 粒度 | 任务级 + 专业级双粒度 | 任务级（周） |
| 与 04 关系 | T096-T135 的 470 项实施明细在 04 系统集成管理 | 不重叠 |

### 1.2 与混合模式的核心冲突

混合项目管理 = **预测型骨架**（范围、里程碑、基线承诺固定）+ **适应型执行**（近期任务滚动排产、周交付、持续复盘）。当前结构有四处不匹配：

1. **双重维护**：任务执行状态同时存在三份——总控四专业 16 列（人工）、周迭代明细（公式引用总控）、04 实施明细（人工）。同一事实三处录入，漂移只是时间问题（联动审计已在用文本匹配兜底）。
2. **总控过重**：135 行 × 31 列，其中 16 列是专业执行明细。预测型骨架真正需要承诺的是**范围 + 里程碑 + 基线日期**，专业级执行过程属于适应层，不应压在基线台账上。
3. **状态不同源**：总体状态（G 列）是人工下拉，与四专业状态、迭代完成情况无公式联动——"状态三选一不一致"无法被机制发现。
4. **无预测口径**：总控只有基线日期（公式推导），没有"当前预测完成日期"——预测型管理的核心指标**基线偏差**算不出来；里程碑计划已有偏差天数公式，但总控任务层没有向上汇总的预测口径。
5. **滚动纪律缺失**：迭代周列刚建成，还没有"只排近期 2-4 周、滚动填充"的规则约定；汇总区 24 行容量对全周期 70+ 周不足（混合模式下只需近期窗口，容量反而够用）。

另发现一处技术债：总控 AC 列（延期状态）公式硬编码了 `DATE(2026,9,1)` 数据日期，随时间推移会过期，应改为引用数据日期单元格。

## 二、目标模式：两簿分工

```
里程碑计划（预测骨架：阶段门禁，基线 vs 预测偏差）
      │ 批次（MSxxx）
      ▼
项目总控台账（范围基线：特性/工作包级承诺——日期、主责、状态、阻塞）
      │ 迭代周列（滚动排产：只排未来2-4周）
      ▼
周迭代计划（适应执行：周承诺、每日站会阻塞、迭代评审/复盘）
      ▲
资源计划（容量约束：人×周 40h，排产即校验）
```

**一句话分工**：总控回答"承诺了什么、偏差多大"；迭代计划回答"这周交付什么、阻塞什么"；两者通过迭代周列和状态回算公式闭环，不再有两份人工状态。

## 三、优化建议（按优先级）

### P0 立即可做（不改结构，只加公式/纪律）

1. **总控状态回算**：总体状态（G 列）改为公式——按该任务在迭代明细中的完成情况自动得出：无迭代周指定→"未开始"；明细全部"已完成"→"已完成"；否则→"进行中"；人工仅保留"暂停"覆盖值。消除状态双重维护。技术点：COUNTIFS（迭代明细 B:B=任务ID, I:I="已完成"）。
2. **增加"预测完成日期"列**：人工维护（每次迭代评审后刷新），延期状态与里程碑偏差改为用预测日期计算。这是混合模式 steering 的核心指标：**基线完成（J 列） vs 预测完成**，偏差天数 = 预测 - 基线。
3. **滚动窗口纪律写入使用说明**：迭代周列只指定未来 2-4 周；迭代复盘会后滚动填充下一周；超过窗口的留空。配套：周报增加"滚动排产覆盖周数"一行。
4. **修复 AC 列硬编码日期**：`DATE(2026,9,1)` 改为引用 `_数据接口` 或总控顶部数据日期单元格。
5. **迭代汇总增强**：汇总区每周增加"容量人时"（引用资源计划该周人数×40）与"负载率=明细任务数×40/容量"，排产时即可见超负荷，不必等 Agent 巡检。

### P1 评审后实施（涉及结构，走变更流程）

6. **总控四专业 16 列瘦身**：四专业执行明细的执行记录职责移交周迭代明细（增加"专业阶段"取值规范：业务/后端/前端/测试）与 04；总控仅保留主责人 + 总体状态。计划开始/完成从"四专业日期推导"改为"基线日期人工维护 + 预测日期滚动刷新"。**影响面大**（综合进度公式、筛选视图、Agent 规则、驾驶舱口径都引用这些列），须专项评审。
7. **任务分层语义明确**：一级功能=领域（范围基线，冻结）；二级=里程碑工作包（预测）；三级=特性（可在迭代间流动）；四级=执行（仅存在于迭代/04）。当前 135 任务中纯执行任务逐步转为"迭代驱动"标识，不再逐个维护基线日期。
8. **迭代明细增加优先级与需求追溯列**：P0/P1 优先级下拉 + 需求ID（关联 03 范围基线），支撑迭代计划会排序与范围蔓延度量。

### P2 机制配套

9. **会议节奏固化**：里程碑评审（门禁，预测型）+ 迭代计划会（每周滚动排产）+ 站会（阻塞写入迭代明细"异常提示"）+ 迭代评审/回顾（结论写入复盘结论列）。08 沟通目录已有周报与会议机制，补充迭代仪式即可。
10. **度量看板**：驾驶舱或周报增加三个混合指标——里程碑基线偏差（天）、迭代承诺完成率（周汇总 H 列已有）、滚动窗口覆盖率（已指定迭代周的任务/计划启动任务）。Agent 规则层已有跨期记忆，指标可直接取数。

## 四、实施顺序与边界

- 顺序：P0-4 修复 → P0-1/2/3/5（一个迭代周期内可落地）→ P1 评审 → P2。
- P1-6 是结构变更，**等于修改范围基线的承载方式**，按治理规则须经评审批准，且实施时备份 + 联动审计 + 全量回归。
- 所有公式改动遵守现有纪律：TDD、officecli 校验、Agent 分析链回归、数据血缘文档同步。

## 五、当前数字化基础已具备的条件

- 迭代周列 + 生成命令（刚建成，滚动排产的入口已就绪）
- 明细 INDEX/MATCH 联动（状态回算的公式基础已就绪）
- 资源计划人×周容量数据（负载校验的数据已就绪）
- 里程碑偏差天数公式（预测口径的示范已存在）
- Agent 巡检跨期记忆（偏差趋势自动可见）

**结论**：混合转型不需要重建工具，需要的是三件事——状态单源化（P0-1）、预测口径补齐（P0-2）、滚动纪律成文（P0-3）。P1 的 16 列瘦身是最大收益也是最大变更，建议在 10-20 启动决策前后安排专项评审。
